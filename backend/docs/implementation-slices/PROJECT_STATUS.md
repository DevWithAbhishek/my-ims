## 5. Current Implementation

- Entrypoints: `src/main.ts` (API, honors `config.port`, fail-fast on DB/Redis, graceful shutdown) and `src/worker.ts` (bootstrap shell, no workers). `src/server.ts` removed.
- `src/config/env.ts`: Zod-validated config (`parseConfig`, memoized `getConfig`); errors name variables only. `.env.example` added.
- `src/app.ts`: `createApp({ readinessChecks, apiRouter })`; request-id, pino-http (method/path/status only), JSON limit `100kb`, `/health`, `/ready`, `/api/v1` mount, error middleware. `GET /` removed.
- Errors: `AppError` with `details`, `retryAfterSeconds`; classes for 400/401/403/404/409/413/422/429/500/503; envelope `{ error: { code, message, details, requestId } }`; Zod → 422 `VALIDATION_FAILED` (unknown keys → 400 `BAD_REQUEST`); body-parser errors → 400; unknown errors → 500 `INTERNAL_ERROR` logged at `error` with stack. Helper `parseOrThrow`.
- Infra: `src/infra/db/prisma.ts` (Prisma 7 + pg adapter, pool max 10, `runInTransaction`, `lockRowForUpdate`, `pingDatabase`), `src/infra/redis/redis.ts` (`createRedisConnection('general' | 'bullmq')`, `getRedis`, `pingRedis`, `closeRedis`), `src/infra/readiness.ts`.
- Tooling: ESLint boundaries match `src/modules/<name>/**`, `src/infra`, `src/shared`, `src/workers`; `prisma.config.ts` (renamed from `prisma7.config.ts`); compose has PostgreSQL (healthcheck user fixed) and Redis (`noeviction`, AOF).
- Tests: `src/**/*.spec.ts` (unit), `test/integration/*.int-spec.ts`, helpers in `test/helpers`.

- `src/modules/identity/` (single module; `auth/`, `teams/`, `users/`): controller → service → repository per area. Public interface (`index.ts`): `authenticate`, `requireRoles`, `requireTeam`, `assertSameTeam`, `getAuth`, `createIdentityRouter`, `seedAdminUser`. Composition in `src/api-router.ts` (used by `main.ts` and `test/helpers/app.ts`).
- Tokens: HS256 JWT (15 min) from `JWT_SECRET`; refresh cookie value `<sessionId>.<base64url(email)>.<secret>`, only SHA-256 of the secret is stored; `Set-Cookie` built by hand to carry exactly the specified attributes. Passwords: Argon2 default configuration.
- Rate limiting: Redis Lua script (atomic counter + ladder 10 min → 20 min → 60 min → 4 h → 24 h IP block); fails closed with 503. Keys hold hashes, never raw emails or IPs.
- Lint: one boundaries rule lets every module import `identity` through its `index.ts` (enforced; verified with temporary files).
- Shared additions: `src/infra/db/errors.ts` (unique violation / concurrency failure detection), `src/shared/middleware/json-body.ts` (non-JSON body → 400).
- `.env.example` (was missing from the repo) with the seed variables `SEED_ADMIN_NAME/EMAIL/PASSWORD`.

- `src/modules/appService/` (`services/`, `escalation-policies/`): controller → service → repository per area, mounted in `src/api-router.ts` via `createAppServiceRouter()`. Public interface (`index.ts`): `createAppServiceRouter`, `getServiceConfig(serviceId)` → `{ id, name, status, teamId, defaultSeverity, escalationPolicyId, sla: { P0..P3: { responseMinutes, resolutionMinutes } } }` or `null`, `getEscalationPolicyByService(serviceId)` → `{ level1, level2, level3, fallbackAdmin }` or `null`. Pure rules with unit tests: `sla.rules.ts` (ordering on merged values), `policy-users.rules.ts` (role/team/status per level).
- Concurrency: S4/S7 lock the `AppService` row `FOR UPDATE` and re-check incidents under it (an in-flight incident insert holds a key-share lock on that row, so the check waits for it; proven by tests that hold an uncommitted incident insert on a second connection). S1 and S4 team changes take `FOR SHARE` on the `Team` row (closes the race with T4's attached-services check); S1/S7 read policy users `FOR SHARE`; S4 policy reassignment locks the policy row so two services cannot claim one orphaned policy.

Layout: `incident.{controller,service,repository,mapper,schema}.ts` (I1, I2), `timeline/` (I11), `comments/` (I10 handler and repository), `update/` (the `PATCH /incidents/:incidentId` dispatcher skeleton: full strict `UpdateIncidentDto`, rows registry `UPDATE_ROWS`, `selectRow` = exactly one row else `422`; only the `comment` row exists), pure units `sla.ts`, `cursor.ts`, `ai-triage.ts`, `timeline/timeline.mapper.ts`, shared `incidents.common.ts` (`assertIncidentAccess` = 404 / `403 TEAM_ACCESS_DENIED`, `runIncidentTransaction`, `withDatabaseOutageMapping`).

Unknown keys are never exposed. Documented in `timeline/timeline.mapper.ts`.

- **SLICE-03.** `src/modules/alerts/`, mounted at the **application root** (not `/api/v1`) through the new optional `createApp({ webhookRouter })`, which is placed before `express.json()` (the signature covers the raw bytes and the limit is 1 MB, not 100 kb); `main.ts` and `test/helpers/app.ts` pass `createWebhookRouter()`. - **Hand-over from SLICE-03 (realized in SLICE-04).** `createWebhookRouter({ ingest })`: `ingest(context: VerifiedAlertContext) => Promise<IngestResponse>` with `IngestResponse = { statusCode: 200 | 400, body }` (SLICE-03 returned a bare body and always sent `200`; the change lets ingestion answer `400` when every alert was rejected). `VerifiedAlertContext = { alertSource: { id, name, sourceType, configuration }, items: unknown[] (≤ 100, request order), rateLimitedIndices: number[], requestId }`. The route stays under test control through `Partial<WebhookDeps>` (`findSource`, `replayStore`, `rateLimiter`, `notifyBlocked`, `ingest`, `now`); the default `ingest` is `createIngestHandler()`.
- **Redis state (all ephemeral).** `wh:replay:*`; `wh:rl:count|block|level|notice|notice-lock:<sourceId>`. Fixed 60 s window, capacity 15 alerts. Ladder 5 min → 20 min → 45 min → 2 h; the fifth violation (and every later one) starts the final block (24 h) and writes the Admin notice. Ladder memory 24 h, refreshed by each violation. All values are constants in `webhook.config.ts`.
- **Admin notice.** `enqueueOutbox` in its own transaction: `NOTIFICATION_REQUESTED`, `aggregateType` `ALERT_SOURCE`, `aggregateId` = source id, payload exactly `{ kind: 'ALERT_SOURCE_BLOCKED', alertSourceId, attemptCount, requestId }` (`attemptCount` = number of violations, so 5 for the first final block). The violation that starts the final block writes it; the Lua script marks the notice `pending:<level>` and takes a 10 s claim, a blocked request that finds a `pending` notice (the write failed) claims and retries it, and a successful write marks it `sent`. No timeline event is written.
- **Seed.** Existing source = the seeded `SEED_ALERT_SOURCE_ID`; the existing row is locked `FOR UPDATE`, the new configuration is `{ ...existing, signingSecret, severityMapping }`, and a differing key set is audited in the same transaction as the update (`ALERT_SOURCE_UPDATED`, `actor = null`, `incidentId = null`, metadata `{ alertSourceId, changedKeys }` = sorted key names only). Creation and an unchanged re-run write no audit event.

- **SLICE-04.** `src/modules/alerts/` gains `alert-input.ts` (Zod `CommonAlertInputDto` → `NormalizedAlert`), `identity.ts`, `severity.ts`, `incident-text.ts`, `alert.repository.ts`, `ingest.service.ts` (`createIngestHandler(overrides?)`, exported), `ingest.types.ts`, `outage.ts`, and for I12 `alert.controller.ts` / `alert.service.ts` / `alert.mapper.ts` / `alerts.routes.ts` (`createAlertsRouter()`, mounted in `src/api-router.ts` under `/api/v1`, any authenticated role). `src/modules/incidents/index.ts` now also exports `createIncident(tx, input)` (takes `FOR SHARE` on the team row, inserts an `OPEN` incident; known issue 8) and `assertCanAccessIncident(auth, incidentId)` (team → 404 → team match). `ingest.placeholder.ts` is deleted.
- **Ingestion flow (W1 step 7).** Per alert, in request order, each in its own transaction: rate-limited index → `RATE_LIMITED` (not validated); validate → `ALERT_INVALID`; service lookup via `getServiceConfig` (cached per request) → `UNKNOWN_SERVICE` / `SERVICE_DEACTIVATED` (applies to `RESOLVED` deliveries too); identity → `IDENTITY_UNRESOLVABLE`. `FIRING`: look up the active key; found → `DUPLICATE` + `ALERT_DUPLICATE` audit on the existing incident; otherwise derive title/description (neither name nor summary → `ALERT_INVALID`, nothing written), then create incident, alert (carrying `activeIdentityKey`), audit `INCIDENT_CREATED` + `ALERT_RECEIVED` (actor `null`), and outbox `ALERT_TRIAGE_REQUESTED` (aggregate `ALERT`) + `SLA_EVALUATION_REQUESTED` (aggregate `INCIDENT`), payloads ids + `requestId`, all in one commit. A unique violation on `(alertSourceId, activeIdentityKey)` rolls the loser back and it is handled once more in a new transaction (→ `DUPLICATE`); a test forces that path. `RESOLVED`: the most recent alert of the source with the same `sourceEventId` / `sourceFingerprint` (`createdAt`, `id` descending), row locked `FOR UPDATE` and re-checked, `sourceStatus` / `endedTimestamp` / `updatedAt` written and `SOURCE_ALERT_RESOLVED` appended once; incident status and `activeIdentityKey` are untouched; none found → `ALERT_INVALID`. Response `200`, or `400` with the same body when every item is `REJECTED`. A database outage → `503 DEPENDENCY_UNAVAILABLE` + `Retry-After: 5` (alerts already committed stay committed; a retry reports them as `DUPLICATE`); any other failure → `500`.
- **Identity.** `sourceEventId` → key `event:<id>`; else `sourceFingerprint` → `fingerprint:<fp>`; else a derived fingerprint (SHA-256 hex of JSON `[serviceId (lower-case), name|null, environment, sorted labels]`, stored in `Alert.sourceFingerprint`) → `fingerprint:<hash>`; none of these possible (no name and no labels) → `IDENTITY_UNRESOLVABLE`. Severity: `configuration.severityMapping` keyed by the lower-cased source severity (case-insensitive, otherwise exact); unrecognized, absent, or no mapping → the service default.
- **I12.** Order: `422` ids → `401` → `403 INVALID_ACTION` (`teamId = null`, also for an Admin) → `404 INCIDENT_NOT_FOUND` → `403 TEAM_ACCESS_DENIED` → `404 ALERT_NOT_FOUND` (also when the alert belongs to another incident). `originalPayload` is returned only here; `startedTimestamp` / `endedTimestamp` are exposed as `startedAt` / `endedAt`.

Not present: any module other than `identity`, `appService`, `incidents` and `alerts`, any consumer registered on a queue, delivery of the `ALERT_SOURCE_BLOCKED` notice (SLICE-09), any alert-source management API (none exists by design).

## 6. Known Issues

1. ESLint uses the legacy boundaries rule syntax (deprecated in eslint-plugin-boundaries v7); migrate to `boundaries/dependencies` in a tooling follow-up.
2. Integration helpers import `pg`, typed only via a transitive `@types/pg`; declare it as a devDependency if kept.
3. Unknown routes return Express' default 404 (not the error envelope); the slice does not define a route-not-found code.
4. Oversized JSON bodies on `/api/v1` return `400 BAD_REQUEST` per SLICE-00 §4.2. The `413 PAYLOAD_TOO_LARGE` class is now used, by the webhook only (1 MB, own raw-body reader).
5. The rate limiter keys on `req.ip`; `trust proxy` is not configured, so behind a reverse proxy all clients share the proxy's IP. Configure it at deployment.
6. The refresh-cookie email is client-controlled until the token is validated; it only feeds the A2 limiter key (project-owner decision) and never authorization.

19. SLICE-03 interpretation choices where the slice is silent (the defaults chosen; override any of them in a follow-up): (a) a **violation** (the step that moves the ladder) is a request that arrives with **no capacity left**; a batch that is only partly accepted is not a violation, and requests that meet a block do not escalate it further. (b) Ladder memory and the final block are both **24 h**. (c) A signature stays in the replay store even when a **later step rejects** the request (`429`, `400`, `422`, `503`), as the step order implies, so a sender must re-sign with a fresh timestamp to retry; re-signing within the same second yields the same signature and is `409 REPLAY_DETECTED`. (d) A request that passes step 5 and fails step 6 (for example 101 alerts) has **already used up its rate-limit capacity**. (e) `Content-Type` that is missing or not `application/json` (charset allowed) is `400 BAD_REQUEST`; an unknown top-level body field is `400 BAD_REQUEST` (AGENTS strict-DTO rule); `alerts` that is not an array is `422`. (f) A blocked source is answered `429` before the body is looked at, even if the body is malformed; a body with nothing to count (malformed, no array, empty array) never consumes capacity. (g) The window is a **fixed** 60 s window (a sender can burst up to 30 alerts across a boundary). (h) Seed: the existing source is identified by `SEED_ALERT_SOURCE_ID`; `SEED_ALERT_SOURCE_NAME` and the status are applied on creation only (a re-run never renames, reactivates or deactivates); other configuration keys are preserved; the signing secret must be at least 32 characters; an omitted `SEED_ALERT_SOURCE_SEVERITY_MAPPING` means the four defaults, so a re-run without it resets a customised mapping and audits `severityMapping`. (i) If the notice write fails, the `429` is unchanged, the failure is logged, and the next blocked request retries it after the 10 s claim expires; if Redis fails between a successful write and its acknowledgement, the notice can be written twice (the consumer, SLICE-09, should be idempotent on the outbox id). (j) A source with a missing or non-string `signingSecret` is treated like an unknown source (`401 SOURCE_AUTH_FAILED`). (k) `X-Request-Id` is optional and handled by the existing global request-id middleware. (l) Only an unreachable database (`isDatabaseUnavailable`) on the source lookup is `503`; any other database error is `500 INTERNAL_ERROR`. (m) Not tested automatically: the log output (no code path logs a secret, a signature or the body; verified by review and by the runtime run in §4), and a database outage on the lookup at integration level (unit-tested with an injected failure).

22. **SLICE-04 migration deviates from the init migration.** `uq_alert_source_event_id` and `uq_alert_source_fingerprint` (partial *unique* indexes) are dropped and replaced by the non-unique `idx_alert_sourceId_sourceEventId` and `idx_alert_sourceId_fingerprint`, because identity must repeat: after an incident is resolved, a new `FIRING` delivery creates a new alert with the same `sourceEventId` / fingerprint. SLICE-04 interpretation choices where the slice is silent: (a) `name`, `environment` and `summary` must be non-empty; `description` / `additionalDetails` may be empty; (b) `sourceUrl` must be an `http` or `https` URL; (c) unknown fields are tolerated and an optional field must be absent, not `null`; (d) a NUL character anywhere in an element makes it `ALERT_INVALID` (PostgreSQL text/`jsonb` cannot store it); (e) a `RESOLVED` delivery without `endedAt` stores the time of receipt in `endedTimestamp`; (f) `ALERT_INVALID` carries field names only (never values) in its `message`; (g) outbox `aggregateType` is `ALERT` for `ALERT_TRIAGE_REQUESTED` and `INCIDENT` for `SLA_EVALUATION_REQUESTED`; (h) only a database outage maps to `503`; a lock timeout or deadlock inside ingestion would surface as `500`; (i) `Alert.updatedAt` has no `@updatedAt`, so the resolved update sets it explicitly; (j) alerts of one request run strictly in order, which makes two same-identity alerts in one batch deterministic (first creates, second is a duplicate).
